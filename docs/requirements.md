# sundesk 要件定義

- 状態: ドラフト（話し合いながら更新中）
- 最終更新: 2026-09-29

## 1. コンセプト

> **自分の知識グラフの上で、ローカル AI を動かし、覗き、いじる実験場**

sundesk は自分専用の macOS アプリ。学習・研究ノートを知識として取り込み、
そこから概念と関係の知識グラフを作り、出典つきの RAG で問いに答え、
Hugging Face のモデルを入れて中身を観察したり手を加えたりできる場所にする。

データを保存するだけの箱にはしない。

## 2. 背景と課題

- 情報が散らばっている（Notion、Apple 純正アプリ、Markdown の直書き）
- 書いたものが見つからない
- 知識は `study-artifact` に 549 本の Markdown として蓄積されている

## 3. 利用者と利用形態

| 項目 | 内容 |
|---|---|
| 利用者 | 自分ひとり |
| プラットフォーム | macOS のみ（当面） |
| 使い方 | 「さっと呼び出す道具」ではなく、じっくり触る**実験場** |
| 外部サービス連携 | しない（ローカルで完結） |
| 開発機 | Apple M3 / メモリ 16GB / macOS 26.5 / Xcode 26.6 |

## 4. 機能要件

### F1. 知識の取り込み（study-artifact）

- `study-artifact/notes/` を知識源として読み込む
- ノートの形式:
  - YAML フロントマター（`title` `status` `tags` など）
  - ノート間リンクは `[[数学/線形代数/射影|射影]]` の形。slug は番号の接頭辞（`01-` など）を除いたパス
  - 数式 `$...$` `$$...$$`、注記 `> [!note]`
- ノートの変更を検知して、索引・グラフ・埋め込みを更新する
- ノートの表示（数式を含む）

### F2. 知識グラフ

- **アルゴリズム中心で作り、自動で採用する**（人の確認は挟まない）
- 概念（点）の抽出
  - 日本語の形態素解析で、名詞の連続を専門用語の候補にする
  - TF-IDF や C-value などで、重要な語を選ぶ
- 関係（線）の抽出
  - 共起: 同じ段落・節に出る語を結ぶ（PMI などで偶然の組を除く）
  - 文書構造: 見出しの階層、箇条書きの親子、既存の `[[リンク]]`
  - 文型: 「A とは B である」「A は B の一種」などのパターン
  - 意味の近さ: 埋め込みベクトルの類似度
- 分析: PageRank（中心的な概念）、コミュニティ検出（分野のまとまり）
- 可視化して眺めて楽しめること
- LLM は補助に回す（重要な線に関係の種類を付ける、など）。後回しでよい

### F3. RAG（自分のメモを参照して答える）

- **答えの根拠になったメモを出典として示す**
- 検索は組み合わせる: 全文検索、ベクトル検索、知識グラフの近傍
- 日本語の埋め込みモデルの候補: ruri-v3

### F4. ローカル LLM の実験室

- Hugging Face の新しいモデルを取り込んで動かす
- Apple Foundation Models も選択肢として残す
- 覗く・いじる:
  - トークンの区切られ方と、次のトークンの確率分布
  - 生成パラメータ（温度など）による出力の変化
  - Attention の可視化
  - 各層の活性、logit lens
  - 活性の操作（steering）
  - LoRA による追加学習

### F5. 画像生成

- **最初から入れる**
- 16GB で現実的な候補: FLUX.2 klein 4B、Z-Image Turbo（4bit）。どちらも mflux で動く
- M3 での 1 枚あたりの生成時間は未計測

## 5. 非機能要件

- ローカルで完結する（モデルのダウンロードを除き、通信しない）
- M3 / 16GB で実用的に動く。モデルは概ね 9B 以下、LoRA は 0.5〜4B 程度を想定
- 自分専用なので App Store 向けの制約（App Sandbox など）には縛られない
- **Mac 標準アプリのように洗練された見た目と操作感にする**
  - Human Interface Guidelines に沿う。macOS 27 のデザイン（Liquid Glass）、標準のコントロール、SF Symbols、システムカラーを使う
  - サイドバー・ツールバー・インスペクタの標準的な構成にする
  - メニューとキーボードショートカットを網羅する。Settings のウインドウを用意する
  - ダークモード、アクセシビリティ（VoiceOver、キーボードだけでの操作）に対応する
  - ウインドウの状態を復元し、取り消し（Undo）ができるようにする

## 6. データ設計の方針

**C 案: ファイルと DB の併用**

| 置き場所 | 持つもの |
|---|---|
| Markdown ファイル | ノート本文。これが正（study-artifact） |
| SwiftData | 構造化データ、索引、知識グラフ（点と線）、実験の記録など |
| SwiftData | 埋め込みベクトル（バイト列として保存し、検索するときはメモリ上で総当たりにする） |
| アプリのデータフォルダ | 画像やテンソルなどの大きなファイル。SwiftData にはそのパスだけを持つ |

- **SwiftData を唯一の DB にする。** AI や解析のエンジンは状態を持たず、計算結果を返すだけにする。保存するのはアプリ側
- 知識グラフの線は、リレーションでたどらずに、ID だけの単純な表として持つ。計算するときにメモリに展開する

### SwiftData のモデル（案）

| モデル | 持つもの | 役割 |
|---|---|---|
| Note | パス、slug、タイトル、タグ、状態、内容のハッシュ、更新日時 | ノートの目録（本文はファイルが正なので持たない） |
| Chunk | ノート、見出しの階層、テキスト、埋め込み | RAG の検索単位。出典として節まで示す |
| Concept | 語、正規形、重要度（PageRank）、コミュニティ | 知識グラフの点 |
| Mention | 概念 ID、チャンク ID、出現回数 | 概念とノートを結ぶ |
| Relation | 始点 ID、終点 ID、種類、重み、根拠のチャンク | 知識グラフの線 |
| ChatSession / Message | 質問、回答、引用したチャンク | RAG の会話。**あとから見返せるように残す** |
| ModelEntry | HF の ID、種類、保存場所、サイズ | 手元のモデルの管理 |
| Experiment | モデル、プロンプト、パラメータ、結果ファイル、メモ | 中身を覗いた実験の記録 |
| GeneratedImage | プロンプト、モデル、シード、パラメータ、画像のパス | 画像生成の履歴 |

細部の方針:

- 変更の検知: ファイルのハッシュを比べ、変わったノートだけ作り直す
- 知識グラフ: 毎回全部作り直す（アルゴリズムなので速い）
- 表記ゆれ:
  - 全角と半角、大文字と小文字など、機械的に同じと言えるものだけを同じ概念にまとめる
  - 「固有値分解」と「固有値」のような複合語は別の概念のまま残し、包含の関係で結ぶ
- 実験の記録:
  - 軽い情報（モデル、プロンプト、パラメータ）は毎回自動で残す
  - 重いデータ（Attention の行列など）は、明示的に保存したときだけ残す

### メモリの運用

- 大きいモデル（LLM か画像生成）は一度に一つだけ載せ、機能を切り替えるたびに自動で入れ替える
- 小さい埋め込みモデルは常に載せておく

## 7. アーキテクチャ（検討中）

AI の実行や解析をどの言語で書くかを検討している。
他の言語を入れることに抵抗はなく、**最適な技術を選ぶ**方針。

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A. Swift のみ | mlx-swift を使い、アプリ内で AI を動かす | 1 つの .app で完結する | 新しいモデルへの対応が遅れがち。解析や NLP の道具が少ない |
| B. Swift + Python | 画面と DB は Swift、AI と解析は Python（mlx-lm など）の別プロセス | 新しいモデルや解析ライブラリがそろう | 構成が複雑。Python 環境の管理が要る |

### 調査結果（2026-09-29）

**B（Swift + Python）に決定した（2026-09-29）。**

| 機能 | Swift 側 | Python 側 | 推奨 |
|---|---|---|---|
| チャット推論 | mlx-swift-lm（モデル実装 約 60） | mlx-lm（約 134、新モデルが先に入る） | Python |
| Attention・logit lens・steering | モデルのクラスが internal なので、コードをコピーして改変する必要がある | 関数の差し替えで取れる。mlxterp（MLX 用、小規模）や TransformerLens / nnsight（PyTorch + MPS）もある | Python |
| LoRA | `LoRATrain` はあるが最小限 | `mlx_lm.lora`（LoRA / DoRA / 全体学習）、mlx-lm-lora | Python |
| 画像生成 | flux-2-swift-mlx、zimage.swift | mflux 0.20（FLUX.2 klein、Z-Image など） | Python |
| 形態素解析・用語抽出 | NLTagger は日本語の品詞を出せない。Mecab-Swift のみ | Sudachi、GiNZA、termextract | Python |
| グラフのアルゴリズム | 自前で実装することになる | networkx、igraph、leidenalg | Python |
| グラフの可視化 | WKWebView + sigma.js / cosmos（WebGL、大規模向け） | — | Swift |
| 埋め込み（ruri-v3） | そのままでは動かない（Core ML に変換するか、Qwen3-Embedding で代替） | sentence-transformers で確実に動く | Python |
| ベクトル検索 | 総当たりで十分 | 総当たりで十分 | どちらでも |
| 保存・画面・ヒートマップ | SwiftData、SwiftUI Canvas | — | Swift |

補足:

- Attention の重みは、高速化された計算に隠れていて、どちらの言語でも標準では返ってこない。可視化するときだけ計算を分ける
- Apple 純正の画像生成は使えない
  - ImageCreator は macOS 27 で廃止
  - 後継の Image Playground は UI 付きのシートのみで、コードから直接生成できない
- 16GB では、MLX のモデルを持つプロセスは 1 つに絞る（Swift と Python で二重に載せない）
- SwiftData に 10⁵ 本規模のエッジを持つなら、リレーションで辿るのではなく、整数 ID のフラットな表にしてメモリ上で隣接リストに展開するのが無難（性能は未検証）

### B 案の構成（案）

- Python の環境: uv で `~/Library/Application Support/sundesk/` 以下に作り、アプリから起動する
- 通信: FastAPI を 127.0.0.1 の TCP で待ち受け、起動ごとのトークンで確かめる（当初案の Unix ドメインソケットから変更。[ADR 0006](adr/0006-engine-http-over-loopback.md)）。トークンの逐次送信は SSE か WebSocket、テンソルは生バイトで送る
- Attention の行列は大きい（1 層で約 16MB）ので、層・ヘッドの選択や間引きはエンジン側で済ませる
- ライフサイクル: 必要になったときに起動し、死活確認をし、アプリの終了時に止める

## 8. 優先順位と進め方

MVP には全機能を入れ、次の順に作る。各フェーズはプルリクエスト単位で進め、テストを書き、
動くものを確かめてから次へ進む。

| フェーズ | 内容 |
|---|---|
| 0. 基盤 | 開発環境、CI、パッケージの骨組み、エンジンの骨組み、アプリの外枠 |
| 1. ノートの表示と編集 | Vault（フォルダ）のファイルを開いて表示し、編集する。Markdown、HTML、テキスト、コード、画像、PDF に対応する。Markdown はライブプレビュー、ソース、閲覧の 3 つのモードで、自動で保存する。study-artifact の取り込みは見送り、当面はモックの Vault で作る |
| 2. 知識グラフ | 形態素解析と用語抽出、関係の抽出、PageRank とコミュニティ検出、Metal での描画 |
| 3. RAG | ruri-v3 の埋め込み、3 種類を組み合わせた検索、出典つきのチャット、履歴 |
| 4. LLM 実験室 | Hugging Face からのモデル管理、トークンの確率分布、Attention、logit lens |
| 5. 画像生成 | mflux で FLUX.2 klein や Z-Image を動かす |
| 6. いじる | LoRA、steering |

画面はメインウインドウを一つにし、機能はタブで開く（ADR 0009）。
